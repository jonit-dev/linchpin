## 1. Context

**The goal, stated plainly:** a run can put a different provider on each role. Saying
*"use Linchpin with Astra medium as reviewer and Opus 5 medium as executor"* resolves to a
`codex exec` reviewer on `gpt-6-astra` at `medium` and a `claude -p` worker on
`claude-opus-5` at `medium`, verified before a branch exists, and recorded in the brief the
worker actually reads.

**Problem.** Every role pin in `references/runtime.md` assumes one provider. Three separate
places hard-code that assumption:

- `scripts/linchpin.sh:110` and `:113` assert the Worker and Reviewer mechanism cells are
  literally `codex exec --sandbox danger-full-access` and `codex exec --sandbox read-only`.
  A Claude Code role cannot be expressed without failing that assertion.
- `alias_model` (`scripts/linchpin.sh:57`) only returns a slug matching `^gpt-`, so a Claude
  model id cannot survive alias resolution even if a row existed for it.
- `preflight_model` (`scripts/linchpin.sh:1521`) verifies every role against
  `$CODEX_HOME/models_cache.json`. Claude Code has no such cache, so the one refusal that
  protects a run from a bad model has nothing to read.

And the model itself can only be changed by editing `.linchpin.toml` by hand.
`references/intake.md:150` already promises that "natural-language overrides are written to
this file before scheduling", but nothing parses a natural-language override; the manager is
expected to improvise the mapping from *"Astra medium as reviewer"* to two config keys, and an
improvised mapping is the thing this repository does not accept anywhere else.

**Files analyzed:**

- `scripts/linchpin.sh` (5138 lines total across the repo) — `runtime_value:34`,
  `alias_model:57`, `runtime_metadata:80`, `config_values:1060`, `brief_emit:831`,
  `brief_check:993`, `review_brief_emit:970`, `preflight_model:1521`, `lane_launch:1706`
- `references/runtime.md` — Role pins, Model aliases, Delegation rules, Invocation shapes
- `references/intake.md:112-155` — the optional `.linchpin.toml` surface
- `skills/prd-swarm-coordinator/SKILL.md:66-119` — the one-command lane start
- `skills/linchpin/SKILL.md:37-56` — dispatch procedure
- `~/.codex/models_cache.json` — codex capability source of truth; contains `gpt-6-astra`
- `claude --help` (Claude Code CLI on PATH) — `--model`, `--effort`, `--permission-mode`,
  `--session-id`, `--print`, `--disallowed-tools`, `--add-dir`

**Verified model ids.** Every Claude id below was probed against the installed CLI on
2026-09-04 with `claude -p --model <id> --effort low --max-turns 1` and returned normally:
`claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5`, `claude-fable-5-1`. The bare aliases
`opus` and `sonnet` also resolve, and are deliberately **not** used as pins: a floating alias
is the stale-pin failure the alias table already exists to prevent. `gpt-6-astra` was
confirmed present in the local codex model cache.

**Current behavior:**

- One provider. `README.md:28` says so: "Codex only. Claude Code is not supported."
- `worker`/`reviewer` in `.linchpin.toml` accept three aliases, all `gpt-5.6-*`.
- Effort is validated against `low|medium|high|max`, which is codex's domain. Claude Code
  also accepts `xhigh`, and a config that asks for it is rejected today.
- A model is selected by editing a file. Nothing turns a sentence into that edit.

### Background: what "provider" has to mean here

A provider is a launcher plus two mechanisms — one that may write, one that may not — plus a
way to verify a model exists before the run starts. Nothing else about a role changes.

| | codex | claude |
|---|---|---|
| Worker mechanism | `codex exec --sandbox danger-full-access` | `claude -p --permission-mode bypassPermissions` |
| Reviewer mechanism | `codex exec --sandbox read-only` | `claude -p --permission-mode plan --disallowed-tools "Edit Write NotebookEdit"` |
| Working directory | `-C <lane>` | process cwd (`launch --cwd`) |
| Prompt transport | `"$(cat <brief>)"` argument | stdin (`launch --stdin`) |
| Effort flag | `-c 'model_reasoning_effort="<effort>"'` | `--effort <effort>` |
| Effort domain | `low`, `medium`, `high`, `max` | `low`, `medium`, `high`, `xhigh`, `max` |
| Continuation | `codex exec resume <id> -c sandbox_mode="danger-full-access"` | `claude --resume <id> -p` |
| Session id | read out of the subprocess output | pre-generated by the manager (`--session-id`) |
| Preflight | `models_cache.json` lookup | one live `--max-turns 1` probe |

Two consequences worth stating before implementation, because both are the kind of thing a
lane discovers the expensive way:

1. **Claude Code has no `-C`.** A worker must be started with its cwd already inside the lane
   worktree. `lane_launch` currently runs the command with `< /dev/null` and no cwd control
   (`scripts/linchpin.sh:1753`), so both are new options on `launch`, not something the
   coordinator improvises with a `cd &&` string.
2. **A review packet must not be interpolated.** `references/runtime.md` already records a run
   that shell-escaped a packet by hand and read `Reading additional input from stdin...` as a
   review verdict. Claude Code reads a prompt from stdin, which removes the hazard entirely
   for this provider; `launch --stdin` is how the brief gets there.

### Background: hardcoded is the floor, not the ceiling

The alias table stays the verified, shipped list — that is what "hardcode the model ids" buys:
a name in that table has been checked against a real CLI, and a run that uses it cannot fail on
a slug typo. But a user naming a model that is not in the table is a normal request, not an
error. `assign` resolves an unknown name live — cache lookup for codex, one probe for Claude —
and, when it verifies, mints a repo-local alias row so the model is still referred to by alias
everywhere downstream. The invariant that survives is the one that matters: **a slug appears
only in an alias table, and no unverified model ever reaches a lane.**

## Checkpoint Protocol

Automated, run from the repository root: `sh scripts/verify.sh` and `sh tests/run-all.sh`.
Per-phase, run the phase's own tests plus `tests/runtime-override.sh` and
`tests/preflight-model.sh` — those two are where a provider change breaks the zero-config run.

Every gate in the Negative Controls table needs its recorded red before the phase that owns it
is complete: apply the named control, capture the exact command, its `RED observed:` line, and
its non-zero exit, and put them in the Gate Evidence table. A gate asserted from a green-only
run is `UNVERIFIED` and blocks delivery.

Manual, once, and not substitutable by a test: one real lane driven end to end with a Claude
Code worker and a Codex reviewer against a throwaway PRD, confirming the worker commits inside
its own worktree, the reviewer cannot write, and the run ledger names both providers. The live
preflight probe spends one trivial request per distinct Claude model; a run that cannot reach
the API fails preflight rather than falling back, and that refusal is the expected result, not
a defect.
